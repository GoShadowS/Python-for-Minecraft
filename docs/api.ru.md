# Публичный API, точки входа и события

Это вся публичная поверхность пакета `pfm` (`python/pfm`, версия `1.0.0`). Единственный API,
который вправе использовать Python-мод. Всё остальное в `python/pfm` приватно (ведущее
подчёркивание) и может измениться.

Python-сторона покрыта 92 модульными тестами в `python/tests`. Вызывающая её Java-сторона
**ни разу не компилировалась**; см. [`testing.ru.md`](testing.ru.md).

## 1. Точки входа

Объявляются в метаданных мода как `package.module:Attribute`. Атрибут может быть:

| Вид атрибута | Что делает PyFM |
| --- | --- |
| класс | создаёт экземпляр один раз без аргументов и хранит его всё время жизни мода |
| объект (любой экземпляр) | использует как есть |
| вызываемый объект (функция, classmethod, лямбда) | вызывает один раз без аргументов |

Один и тот же атрибут используется для всех фаз, поэтому состояние в `self` переживает переход
от `on_initialize` к `on_client_initialize`. (Это была настоящая ошибка, которую поймал набор
тестов: ранняя реализация создавала новый объект точки входа на каждую фазу и молча теряла это
состояние.)

### Хуки жизненного цикла

| Хук | Когда выполняется | Сторона |
| --- | --- | --- |
| `on_initialize(self)` | после создания рантайма мода | обе |
| `on_client_initialize(self)` | запуск клиента | только клиент |
| `on_server_initialize(self)` | запуск сервера | выделенный сервер (и интегрированный, если адаптер его вызывает) |

Отсутствие хука ошибкой не является. `pfm.PHASES == ('initialize', 'client_initialize',
'server_initialize')`, а `pfm.LIFECYCLE` сопоставляет каждой фазе имя её хука.

## 2. События

```python
import pfm

@pfm.event("server_start")
def on_server_start(event):
    pfm.log.info("сервер запущен, хендл присутствует: %s" % (pfm.mc.server is not None))
```

`pfm.event(name)` и его псевдоним `pfm.on(name)` — декораторы. Их можно использовать только
пока Python-for-Minecraft инициализирует мод; в любой другой момент они бросают
`pfm.HandlerError`, а не регистрируют молча обработчик, который никогда не сработает.

Существует девять имён событий. На Fabric и NeoForge они одинаковы:

| Имя | Когда срабатывает | Полезные данные (`event.data`) |
| --- | --- | --- |
| `initialize` | после выполнения общей точки входа | `None` |
| `client_start` | клиент завершил запуск | `None` |
| `client_stop` | клиент останавливается | `None` |
| `server_start` | запускается выделенный или интегрированный сервер | `None` |
| `server_stop` | сервер останавливается | `None` |
| `client_tick` | один клиентский тик, в потоке клиента | `None` |
| `server_tick` | один серверный тик, в потоке сервера | `None` |
| `player_join` | игрок подключился | хендл игрока |
| `player_leave` | игрок отключился | хендл игрока |

Обработчик, бросивший исключение, не останавливает другие обработчики и другие моды.
`pfm.dispatch(name, data)` возвращает `pfm.DispatchReport` с результатами по модам, а
`pfm.fire(name, data)` — способ для мода отправить собственное событие только этому же моду.

Обработчики выполняются в том потоке, который вызвал событие: поток клиента для `client_*`,
поток сервера для `server_*`. PyFM не переносит работу между потоками; обработчик, которому
нужно отложить работу, должен сделать это сам.

## 3. Команды

```python
@pfm.command("pyhello", usage="/pyhello", permission=0)
def pyhello(ctx):
    ctx.reply("привет из Python")
    pfm.log.info("args=%s" % (ctx.args,))
```

`ctx` — это `pfm.CommandContext` с полями `.source`, `.args` (список строк) и методом
`.reply(text)`. Регистрация идёт через мост в загрузчик, который строит настоящий узел команды
(Brigadier на Fabric и NeoForge). `ctx.reply` для источника, который не может принимать
сообщения, молча игнорируется. Имя должно быть одним словом без ведущего слеша;
`pfm.CommandSpec` отвергает всё остальное в момент регистрации, а не в момент выполнения.

## 4. Java-взаимодействие

```python
cls = pfm.java.import_class("net.minecraft.server.MinecraftServer")
```

`pfm.java.import_class(fqcn)` разрешает Java-класс через мост и возвращает то, что отдаёт
рантайм. Это **единственный** поддерживаемый путь взаимодействия.

Что это даёт и чего не даёт:

* даёт класс, так что можно вызывать статические члены и использовать возвращённые экземпляры;
* **не** оборачивает никакой Minecraft API. Нет `pfm.block`, нет `pfm.registry`, нет
  `pfm.screen`. Всё, что выходит за пределы хендлов из §5, — прямое взаимодействие,
  непротестированное и неподдерживаемое;
* не заменяет миксины, access wideners и core-моды. PyFM не может трансформировать классы
  Minecraft.

## 5. Хендлы

`pfm.mc` отдаёт ровно три хендла и только те, которые действительны на текущей стороне:

| Хендл | Доступен на | Содержит |
| --- | --- | --- |
| `pfm.mc.server` | серверная сторона | объект сервера |
| `pfm.mc.client` | клиентская сторона | объект клиента |
| `pfm.mc.player` | клиентская сторона | локального игрока |

На выделенном сервере `pfm.mc.client` и `pfm.mc.player` равны `None`. Запрос хендла, которого
нет на этой стороне, возвращает `None`, а не бросает исключение.

## 6. Логирование

`pfm.log` — готовый логгер; `pfm.get_logger("my area")` создаёт именованный. Вывод идёт через
мост в лог игры с префиксом `[PyFM]`. Уровни: `debug`, `info`, `warn`, `error`.

## 7. Рантайм и интроспекция

| Вызов | Результат |
| --- | --- |
| `pfm.mod_id()` | id этого мода |
| `pfm.side()` | `pfm.Side.CLIENT` или `pfm.Side.SERVER` |
| `pfm.is_client()` / `pfm.is_server()` | булевы значения |
| `pfm.context()` | `ModContext` этого мода (id мода, сторона, метаданные) |
| `pfm.runtime()` | `ModRuntime` этого мода |
| `pfm.runtime_for(mod_id)` | рантайм другого мода, если он загружен |
| `pfm.all_runtimes()` | все загруженные рантаймы |
| `pfm.autodiscover("pkg.handlers")` | импортирует все модули пакета и регистрирует объявленное в них |

`pfm.side()` и `pfm.mod_id()` бросают `pfm.HandlerError` вне рантайма мода — это намеренно,
чтобы мод не мог случайно прочитать контекст другого мода.

## 8. Ошибки

| Исключение | Когда бросается |
| --- | --- |
| `pfm.PyFmError` | базовый класс |
| `pfm.EntrypointError` | точку входа не удалось разрешить, или хук жизненного цикла упал |
| `pfm.HandlerError` | обработчик события упал, или API использован вне рантайма |
| `pfm.BridgeError` | Java-мост сообщил об отказе |

`pfm.format_exception(exc)` печатает трейсбек гостя с id мода, фазой и кадрами
`at file:line`. Упавший мод записывается как упавший; остальные моды продолжают грузиться. Ни
один упавший мод не сообщается как загруженный.

## 9. Чего намеренно нет

* Нет API реестров, блоков/предметов/экранов, датапаков.
* Нет песочницы, нет модели полномочий. См. [`security.ru.md`](security.ru.md).
* Нет интеграции async/await с игровым циклом.
* Нет горячей перезагрузки.
* Нет этапа компиляции, а значит и проверки типов для модов.
